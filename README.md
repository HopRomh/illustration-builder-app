# Конструктор векторных иллюстраций

Веб-сервис собирает композиции из готовой библиотеки векторных объектов: пользователь выбирает объекты, состояние (главный/фоновый), размер (L/S), цветовую схему и формат холста, двигает и поворачивает объекты, а затем экспортирует результат в SVG.

Два сценария:

- **Сценарий 1 — метафора/заголовок → композиция.** Свободный текст разбирается на токены, по тегам и синонимам подбираются объекты, предлагаются три варианта композиции. Опционально подключается LLM через сервер.
- **Сценарий 2 — названия объектов → композиция.** Пользователь вводит «книга, телефон, лампа», сервис находит объекты по названию/тегу/синониму и раскладывает их на холсте.

Сервис **не генерирует новые объекты и не меняет их форму**: доступны только состав, расположение, поворот, состояние, схема, формат и общий масштаб сцены. Экспорт — только векторный SVG.

- Репозиторий: <https://github.com/HopRomh/illustration-builder-app.git>
- Демо на Render: появится после деплоя по `render.yaml` (см. [«Деплой»](#деплой-render)).

## Стек

- **Клиент:** React 18, Vite, TypeScript, Tailwind CSS 4, Zustand, Fabric.js 7.
- **Сервер:** Node.js 22+, Express 5. Один процесс раздаёт `dist/` и API.
- **Тесты:** Vitest.
- **LLM:** только опционально и только через сервер; ключ не попадает в браузер.
- **Хранение:** JSON-файлы и SVG в репозитории, без базы данных.

## Быстрый старт

Требуется Node.js **22+** (поле `engines` в `package.json`).

```bash
npm ci
npm run dev
```

Vite откроет приложение на <http://localhost:5173>. В dev-режиме запросы `/api/*` проксируются на `http://localhost:3000`.

Для проверки API и LLM во втором терминале:

```bash
npm run dev:api
```

Без запущенного API Сценарий 1 продолжает работать через локальный fallback по тегам; LLM просто не используется.

Production-сборка и запуск:

```bash
npm run build
npm start
```

Сервер поднимется на <http://localhost:3000> (порт задаётся переменной `PORT`). Проверка:

```bash
curl http://localhost:3000/api/health
# {"ok":true,"llm":false}
```

`npm run build` выполняет `prebuild` → `sync-library`, затем `tsc -b` и `vite build`. `npm start` запускает `server/index.ts` через `tsx`; `tsx` находится в `dependencies`, поэтому команда работает после `npm ci --omit=dev`.

### Переменные окружения

Скопируйте `.env.example` в `.env` (файл `.env` в git не попадает):

```dotenv
LLM_API_KEY=
LLM_MODEL=
LLM_BASE_URL=
PORT=3000
```

- `LLM_API_KEY` — ключ провайдера; без него используется fallback.
- `LLM_MODEL` — имя дешёвой быстрой модели.
- `LLM_BASE_URL` — опционально, если провайдер не OpenAI-совместим по умолчанию.
- `PORT` — порт Express, по умолчанию `3000`.

## Деплой (Render)

В репозитории лежит `render.yaml` — Blueprint для одного web-сервиса. Express раздаёт собранный `dist/` и API, отдельный статический хостинг не нужен.

1. Запушьте репозиторий на GitHub.
2. В Render выберите **New → Blueprint** и укажите репозиторий (или создайте **Web Service** вручную и повторите команды из `render.yaml`).
3. Задайте секреты `LLM_API_KEY` и `LLM_MODEL` (и `LLM_BASE_URL`, если нужен). Они не хранятся в репозитории.
4. Дождитесь деплоя и проверьте `https://<service>.onrender.com/api/health`.

Ключевые настройки:

| Параметр | Значение |
| --- | --- |
| Runtime | Node |
| Build Command | `npm ci --include=dev && npm run build` |
| Start Command | `npm start` |
| Health Check Path | `/api/health` |
| Node version | `22.12.0` (через `NODE_VERSION`) |

`npm run build` на Render сам вызывает `sync-library` и собирает `dist/`. Каталог, палитры и библиотека SVG лежат в репозитории, поэтому база данных и отдельный storage не требуются.

Для Railway схема та же: build `npm ci --include=dev && npm run build`, start `npm start`, те же переменные окружения.

## Архитектура

### Общая схема

```text
Браузер
  React + Fabric + Zustand
    │  GET /assets/library/...   (SVG объектов и подложек)
    │  GET /data/*.json          (каталог и палитры)
    │  POST /api/metaphor        (только Сценарий 1, опционально)
    ▼
Express (server/index.ts)
    ├── dist/                    статика production-сборки
    ├── /api/health              статус сервера и наличия LLM-ключа
    ├── /api/metaphor            LLM или fallback
    └── SPA-fallback             index.html для клиентских маршрутов
```

Сервер не хранит состояние пользователя: сцена живёт в Zustand на клиенте, история undo/redo — там же. Базы данных нет.

### Хранение и подготовка SVG

```text
assets/raw/                  исходные выгрузки Figma, вручную не изменяются
      │
      │  npm run catalog  (scripts/build-catalog.ts)
      ▼
assets/library/              нормализованные SVG: main/background × L/S + backdrop
data/catalog.json            id, название, теги, варианты, viewBox, файлы
data/palettes.json           3 схемы × 8 цветовых ролей
data/catalog-report.md       отчёт: пары, палитры, предупреждения
      │
      │  npm run sync-library  (predev / prebuild)
      ▼
public/assets/library/       копия для dev и для Vite
public/data/                 catalog.json + palettes.json
      │
      │  vite build
      ▼
dist/                        статика, которую раздаёт Express
```

- `assets/raw/` — источник истины, скрипт его только читает.
- `scripts/build-catalog.ts` определяет тип и размер по папкам, нормализует корневой `<svg>` (viewBox/width/height), собирает пары `main/background`, извлекает палитры из файлов и пишет отчёт.
- `data/object-map.json` содержит ручную карту для файлов без осмысленных имён (`Group ...`) и `referenceScheme` — схему, в которой нарисованы объекты библиотеки.
- `scripts/sync-library.ts` копирует `assets/library/` и JSON в `public/`. Эти копии сгенерированы и не коммитятся (см. `.gitignore`).
- При расширении библиотеки нужно пересобрать каталог: `npm run catalog`, затем проверить `data/catalog-report.md` и обновить `data/synonyms.json`.

### Извлечение и переиспользование SVG

`data/catalog.json` — единственный контракт между библиотекой и клиентом. Для каждого объекта хранится:

```json
{
  "id": "book",
  "name": "Книга",
  "tags": ["книга", "чтение", "учёба", "..."],
  "variants": {
    "main-L":       { "file": "assets/library/main/L/Книга.svg", "viewBox": [0, 0, 1446, 977] },
    "background-L": { "file": "assets/library/background/L/Книга.svg", "viewBox": [0, 0, 1446, 977] },
    "main-S":       { "file": "assets/library/main/S/Group 2136136335.svg", "viewBox": [0, 0, 723, 489] },
    "background-S": { "file": "assets/library/background/S/Group 2136136341.svg", "viewBox": [0, 0, 723, 489] }
  }
}
```

Клиент не держит SVG в бандле: `src/canvas/loadSvg.ts` загружает файл по `fetch`, парсит его и добавляет в Fabric как группу. При каждом импорте все `id` и ссылки `url(#...)` / `href="#..."` получают уникальный префикс — это защищает `clipPath`, маски и градиенты при повторном добавлении одного и того же файла. Разобранные SVG кешируются по пути файла, поэтому повторные добавления не перезагружают сеть.

Каждый инстанс на холсте получает `id="instance-*"`. При экспорте это превращается в именованные группы, по которым удобно работать в Figma.

### Перекраска

- В `data/palettes.json` три схемы (`lilac`, `peach`, `mint`) по 8 ролей: `bg-1..3`, `bg-black`, `obj-1..3`, `obj-white`.
- Объекты библиотеки нарисованы в референсной схеме (`referenceScheme` в `data/object-map.json`, сейчас `lilac`). `src/canvas/recolor.ts` классифицирует **каждый** `fill` и `stroke` по роли независимо: заливка может быть `obj-1`, а обводка — `bg-black`.
- При смене схемы `applyScheme` / `applySchemeToScene` заменяют цвета по ролям, а не по конкретным HEX. Поэтому одна и та же сцена корректно перекрашивается во все три схемы.
- Подложка выбирается по схеме и размеру из `catalog.backdrops`; её пропорции сохраняются, поля вокруг закрашиваются `bg-1`.
- Превью Сценария 1 перекрашиваются до загрузки в `<image>` через `src/canvas/recolorSvg.ts`, чтобы превью совпадало с финальным холстом.
- `#FFFFFF` в подложках трактуется как нейтральный белый, а не как `obj-white`. Отчёт сборки отдельно предупреждает об использовании объектных цветов в подложках.

### Экспорт

`src/canvas/exportSvg.ts` вызывает `canvas.toSVG()`, затем:

1. удаляет растровые `<image>`, `foreignObject` и фильтры;
2. нормализует корневой `<svg>` (namespace, width/height, viewBox);
3. подставляет прямоугольник фона цвета `bg-1` текущей схемы;
4. проверяет, что в SVG не осталось цветов вне палитры, и пишет предупреждение в консоль.

Экспорт сохраняет слои и редактируемые path: SVG открывается в браузере и в Figma. Отдельные объекты нельзя масштабировать — на холсте отключены ручки масштаба, `scale` общий для всей сцены.

### Сценарии

**Сценарий 2 — названия объектов.**

```text
текст → tokenize (запятые/точки с запятой) → matchQuery
      → resolved / ambiguous / notFound
      → composeScenario: первый объект main, остальные background
      → layoutComposition: фокус в центре, support'ы по слотам
```

Поиск учитывает точное имя, тег, префикс, подстроку и fuzzy-совпадение (Левенштейн), плюс `data/synonyms.json`. Неоднозначные совпадения показываются как выбор кандидата.

**Сценарий 1 — метафора/заголовок.**

```text
текст → tokenizeText (стоп-слова, нормализация)
      → scoreItems по тегам/синонимам
      → buildFallbackPlans: V1, V2, V3
      → composeFallbackPlan → composeScenario → layoutComposition
```

LLM опционален: `POST /api/metaphor` возвращает `tags`, `concepts`, `mood`, `focal`; они добавляются к токенам, а `focal` становится подсказкой фокуса. Без ключа, при таймауте или ошибке используется тот же локальный fallback — Сценарий 1 остаётся рабочим.

**Автолейаут.** Фокус ставится в центр, остальные объекты — в углы/середины сторон с минимизацией пересечений. Повороты support-объектов ограничены диапазоном ±6°. Все объекты клампятся в safe-area (8% от края), масштаб сцены не меняется.

## Библиотека

Библиотека содержит **10 объектов**, каждый в **2 состояниях** (`main`/`background`) и **2 размерах** (`L`/`S`), что в сумме даёт **20 базовых иллюстраций** (40 SVG-файлов: 2 состояния × 2 размера). Дополнительно в каталог входят **6 подложек**: 3 схемы (`lilac`, `peach`, `mint`) × 2 размера.

Объекты: книга, кошелёк, лампа, монета, наушники, пазлы, папка, ручка, телефон, тюльпаны.

Ограничения библиотеки:

- В одной сцене нельзя смешивать L и S — размер сцены общий.
- Состояние `background` — монохромный вариант; `main` — цветной.
- Цвета объектов не используются в подложках; подложки могут использовать цвета фона и нейтральный белый.

## AI-инструменты

Проект разрабатывался с помощью AI-ассистентов; все изменения проверялись тестами, сборкой и ручными проверками в браузере.

- **DeepSeek V4.1 Flash Free** (OpenCode) — основной агент: генерация и рефакторинг кода, тесты, документация, разбор ошибок.
- **OpenCode** — harness, в котором работал агент: инструменты чтения/правки файлов, запуск команд, субагенты.
- **Playwright MCP** — автоматизированная проверка интерфейса в браузере: сценарии, скриншоты, клики, проверка экспорта.

LLM в самом приложении — отдельная опциональная интеграция; она не используется для генерации изображений. Все объекты и подложки — готовые SVG из библиотеки.

## Известные ограничения

- **Пан в textarea.** Сочетание «пробел + drag» не работает, пока фокус находится в текстовом поле: сначала кликните по холсту, затем зажмите пробел и тяните.
- **Пять L-объектов без пересечений.** При `scale = 0.4` пять крупных L-объектов физически не помещаются в safe-area без наложений. Автолейаут минимизирует пересечения, но не гарантирует их отсутствие. Для S-объектов (они компактнее) пять объектов помещаются — см. пример 03.
- **S-версии некоторых объектов — масштабированная копия L.** Для `lamp`, `puzzle`, `pen` и `tulips` S-вариант получен масштабированием L, а не отдельной упрощённой перерисовкой. У `tulips` коэффициент ≈ 0.547, у `coin` ≈ 0.532 (тоже масштаб, но не ровно 0.5). Остальные S-ассеты упрощены/перерисованы. Это осознанное ограничение: исходников для перерисовки нет.
- **Повороты в автолейауте ограничены ±6°.** Ручной поворот на холсте не ограничен; ограничение относится только к автоматической раскладке support-объектов.
- **Расширение каталога требует обновления синонимов.** При добавлении объектов нужно дополнять `data/synonyms.json`, иначе свободный текст Сценария 1 будет находить новые объекты хуже.
- **LLM опционален.** Без `LLM_API_KEY`/`LLM_MODEL` Сценарий 1 работает через fallback по тегам; LLM не обязателен для приёмки.
- **Сценарий 2 — только текст.** По ТЗ (скриншоты) пользователь вводит названия компонентов. Загрузки изображений, drag&drop картинок и vision-запроса в проекте нет и не требуется. Если появится требование «собрать по картинке» — это отдельный блокер: нужен file upload, хранение изображения и vision-запрос.
- **`#FFFFFF` в подложках** считается нейтральным белым, а не `obj-white`; это зафиксировано в отчёте сборки.
- **LLM-ключ только на сервере.** Клиент не получает ключ; при недоступности API используется fallback.
